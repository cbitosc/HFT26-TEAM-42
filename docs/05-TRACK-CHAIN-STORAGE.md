# 05 - Track C: Contracts, Storage and Bridge (`contracts/`, `bridge/`)

Owner: Person 2 (bridge) and Person 3 (contracts), for a three-person team. Tooling: Foundry (Solidity ^0.8.24), OpenZeppelin, and a Python (`FastAPI`, `web3.py`) bridge — **not** the TypeScript option the docs originally suggested, since Person 2 already owns `agent/` in Python and this avoids splitting them across two languages. The bridge's HTTP API below is unchanged either way, so the dashboard is not affected by this choice.

## Contracts

### `MemoryRegistry.sol`

Implements `IMemoryRegistry` exactly as in `02-INTERFACES.md`. Logic:

- `submitImprovement`:
  1. Require `entryId` unused and non-empty `cid`.
  2. Require `entryId == keccak256(abi.encodePacked(cid, scoreHashOld, scoreHashNew, taskSignature, author))`. This is the memory-commitment check the PS asks for: it ties the CID to this specific entry, not just a CID stored next to an arbitrary id.
  3. Require `instances[0] == scoreHashOld`, `instances[1] == scoreHashNew`, `instances[2] == 1`.
  4. Call the verifier. Revert `ProofInvalid` on failure.
  5. Store the entry with `verified = true`, `tier = Candidate`. Index by task signature.
  6. Call `RewardEscrow.payReward(author)`. Emit `ImprovementRecorded` and `RewardPaid`.
- `submitNegative`: require `entryId == keccak256(abi.encodePacked(cid, taskSignature, author))`, then store `verified = false`, no reward. Anyone may submit but the dashboard labels it unverified.
- `postEvidence(reusedEntryId, supported, reporterEntryId)`:
  - Require `reporterEntryId` is a verified entry authored by `msg.sender` (this ties evidence to a proven outcome, which blocks spam).
  - Increment `supported` or `contradicted`, then recompute the tier: `1 -> Validated`, `2 -> Trusted`, `3 -> Canonical` (only counting `supported - contradicted`), demote one tier if `contradicted > supported`.
  - One evidence per `(reporter, reused)` pair. No royalty payout (cut for scope — trust tiers are the only consequence of evidence).
- Never delete. `supersedes` just records the link.
- Gas: keep the CID as `string`, keep structs packed, no loops over unbounded arrays in writes. `entriesByTask` is a read helper returning an array (cap at 200 for the view).

### `RewardEscrow.sol`

- Holds ETH, `payReward(address)` callable only by the registry.
- `reward = 0.001 ether`, configurable by owner.
- Per-address daily cap, pausable, owner `withdraw`. Skip silently (emit `RewardSkipped`) if the balance is too low so a dry escrow never blocks memory writes.

### `Verifier.sol`

Generated by the ZK track. Do not edit. If its size or gas is a problem, raise it with the ZK owner immediately.

### Tests (Foundry)

- Valid baked proof accepted, tampered proof rejected, wrong `scoreHash` rejected, `improved = 0` rejected, duplicate `entryId` rejected
- Reward paid exactly once, daily cap enforced
- Evidence: tier progression, no self-evidence without a verified reporter entry, duplicate evidence rejected
- Use the shared vector in `shared/test_vectors.json`

## Storage: Pinata / IPFS

- `POST /pin` uploads the canonical JSON bytes with the Pinata V3 files API (`network=public`), so the CID is the hash of those exact bytes. The file is named `autoevolve-<sha256 prefix>` because `entryId` does not exist until after the CID does.
- Canonicalise JSON before pinning (sorted keys, no extra whitespace) so the CID is reproducible.
- Cache fetched entries on disk keyed by CID (immutable, so the cache never goes stale).
- Offline/fallback: simplified to one path for a three-person team — if the gateway is slow or `OFFLINE=1`, replay from `shared/baked/`. No second-gateway chase.
- Filecoin: mention that Pinata/IPFS content can be backed by Filecoin deals for durability. Do not build it unless everything else is done.

## Bridge service (`bridge/`)

Implements the HTTP API and the SSE event stream from `02-INTERFACES.md`.

- `/submit`: simulate the transaction first (`simulateContract`) and return a clear error on revert before spending gas, then send, wait for confirmation, emit `chain.tx` (pending, confirmed) and `chain.verified` with the decoded `RewardPaid` and tier.
- `/memory`: read `entriesByTask` plus sibling signatures from chain, fetch each CID (cache), compute **confidence** off-chain, and return ranked entries.
  - Confidence: `supported_weighted / (supported_weighted + contradicted_weighted)` with recency weight `0.5^(age_days/7)`, neutral prior 0.5 when there is no evidence, and a decay of 0.05 per 30 idle days. Tier comes from chain counts, confidence is advisory.
- `/events`: SSE multiplexing events pushed by the agents (`POST /events` from the agent) to all dashboard clients. The agent emits the chain events from the bridge's replies, so they carry its `run_id`. Tailing on-chain logs is not built.
- `BRIDGE_TOKEN`: when set, every POST needs `Authorization: Bearer <token>`. Set it on any public bridge, because writes spend the agents' gas.
- `BAKED_PIN=1`: pins locally with a labelled `baked-` CID. For Anvil rehearsals only.
- `/entry/:cid`: gateway bytes are hashed against the CID before they are trusted or cached. Only raw CIDv1 (`bafk...`) can be checked locally.
- `OFFLINE=1`: serve everything from `shared/baked/`, and fake tx hashes visibly labelled `baked`. The dashboard shows a small "replay" badge so we never misrepresent it.
- Keys: agents sign their own transactions where possible. If the bridge signs, it uses per-agent keys from env. No keys in responses or logs.

## Seeding for the demo

Script `bridge/scripts/seed.py --runs <run_id> ...` replays entries recorded under `runs/<run_id>/entries/` onto the registry, rebound to the agent wallets, with real Poseidon commitments and proofs. It never takes hand-written lessons: if Agent B inherited lessons written by someone who knows the task's traps, the A/B result would prove nothing. Evidence is not seeded either, so tiers only move when an agent really reuses an entry. Store the seed CIDs in `shared/baked/seed.json`.

## Definition of done

1. Contracts deployed and source-verified on Sepolia, addresses in `shared/deployments.sepolia.json`.
2. `curl` of `/pin`, `/submit` with the baked proof from the ZK track results in a confirmed tx, a reward received, and an SSE event.
3. `/memory?task=...` returns ranked entries with tiers and confidence.
4. `OFFLINE=1` replay works with no network.
5. Seed script has run on Sepolia.
